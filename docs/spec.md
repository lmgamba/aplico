# Aplico — spec

**One sentence:** a private kanban board of the jobs I have applied to, deployed publicly as a
portfolio piece, built to teach me Spring Boot 4.1 and Angular 22 signals in 3 weeks.

**Not a product.** Success = (a) I use it for my own job search, (b) it is live on a free URL
before any write endpoint exists, (c) it looks right on a phone, (d) I can defend every
decision in it out loud.

**Budget: 18 hours** (6 h/week × 3 weeks). Every estimate below is against that number.

---

## 1. Scope

**In**
- One board, five columns: `WISHLIST → APPLIED → INTERVIEW → OFFER / REJECTED`.
- Create, read, update, delete an application. Move it between columns.
- An automatic timeline of status changes per application.
- Search + filter + per-column counts, all derived client-side with signals.
- **Two environments, two datasets** (see §5a): the public deploy carries fictional seed data
  only; the real job search runs on the local instance.
- Single hardcoded user, HTTP Basic. Reads public, writes authenticated, **cross-origin**.
- Mobile-first: designed at 360 px, widened for desktop.

**Out, deliberately** — each has a written justification in `learning-map.md`:
multi-user, registration, JWT, password reset, email reminders, CV upload, tags, contacts,
interview scheduling, CSV import/export, drag-and-drop, reorder-within-column, pagination,
i18n, an insights/stats screen, optimistic locking.

## 2. Data model — 2 tables

> The ceiling was 3. Two is what the domain needs at 18 hours; `company` is designed below as a
> **deferred** feature, not an omission.

### Why relational at all
- The data is a small set of **uniform, strongly-typed records** with one clear **one-to-many**
  (application → status events). No schema variability, no nested documents.
- The rules I care about are **integrity rules**: an event cannot exist without its application
  (FK), a status must be one of five values (CHECK), a salary range cannot be inverted (CHECK),
  the same role at the same company cannot be entered twice (unique index). In Postgres the
  database enforces them; in a document store I would enforce them in application code and hope.
- **Flyway + SQL gives me a versioned, reviewable schema history** — the thing I actually want
  to learn, and the thing the next project needs.
- Honest caveat for the interview: *at 300 rows any storage engine works.* The reason is
  integrity and learning, not scale. Don't oversell it.

### `application`
| column | type | constraints | why |
|---|---|---|---|
| `id` | `bigint` | `generated by default as identity`, PK | Surrogate key. Not a UUID: single-node, no shard/merge problem, and a `bigint` PK index is half the size. Caveat I must be able to state: `IDENTITY` makes Hibernate disable JDBC insert batching — irrelevant here, decisive in a bulk-import app. |
| `company_name` | `varchar(120)` | `not null`, `check (btrim(company_name) <> '')` | A `not null` column happily accepts `'   '`; the CHECK is what actually enforces "present". |
| `job_title` | `varchar(160)` | `not null`, non-blank CHECK | Named `job_title`, **not** `position` — `POSITION` is a reserved SQL function name and would need quoting forever. Same reason I avoid `user`, `order`, `end`. |
| `source` | `varchar(40)` | `not null`, `check in (...)` | Enum in Java, `varchar` + CHECK in SQL: `LINKEDIN, INFOJOBS, COMPANY_SITE, REFERRAL, RECRUITER, OTHER`. Stored as text so a `SELECT` is readable and reordering the Java enum can't silently corrupt data. |
| `status` | `varchar(20)` | `not null`, `default 'WISHLIST'`, `check in (...)` | The kanban column. Five values. Same enum reasoning. |
| `applied_on` | `date` | nullable | A calendar day, not an instant — "I applied on the 3rd" is timezone-free. Null while `WISHLIST`. |
| `salary_min` | `integer` | nullable, `check (salary_min >= 0)` | Annual gross in whole euros. `integer`, not `numeric`: cents are meaningless in a salary range. |
| `salary_max` | `integer` | nullable, `check (salary_max >= salary_min)` | Table-level CHECK, because it spans two columns. No `currency` column: EUR-only by decision, documented, not forgotten. |
| `job_url` | `varchar(512)` | nullable | The posting. 512 because ATS URLs are long. Format validated in the DTO (`@URL`), not in SQL. |
| `notes` | `text` | nullable | `text`, not `varchar(n)`: in Postgres they are the same type internally and an arbitrary cap on free text buys nothing. |
| `created_at` | `timestamptz` | `not null default now()` | `timestamptz`, never `timestamp` — the API serves UTC, the browser renders local. |
| `updated_at` | `timestamptz` | `not null default now()` | Maintained by Spring Data JPA auditing (`@LastModifiedDate`) in the app **and** defaulted in SQL, so a manual `UPDATE` is still honest. |

Plus: `create unique index ux_application_company_title on application (lower(company_name), lower(job_title));`
→ case-insensitive duplicate protection, and the reason `POST` can return **409**. Trade-off to
say out loud: it also blocks re-applying to the same role a year later; acceptable for a
personal tracker, wrong for a product.

No index on `status` or `applied_on`: with a few hundred rows Postgres will seq-scan anyway and
an unused index is write cost for nothing. *Knowing when you would add one* is the answer.

**Cut for the 18 h budget:** a `version integer` column for optimistic locking (`@Version`).
It was the second-best source of a 409 and a strong interview topic, but with one user and one
browser tab it protects against nothing real. Answer for the interview: *"I left it out and I
can tell you exactly what it would have done and when I'd add it."*

### `application_event`
| column | type | constraints | why |
|---|---|---|---|
| `id` | `bigint` | identity, PK | |
| `application_id` | `bigint` | `not null references application(id) on delete cascade` | The one-to-many. `ON DELETE CASCADE` in SQL **and** `orphanRemoval`/cascade in JPA — I must be able to explain that these are two different mechanisms at two different layers and why I chose belt and braces. |
| `from_status` | `varchar(20)` | nullable, CHECK | Null on the creation event. |
| `to_status` | `varchar(20)` | `not null`, CHECK | |
| `occurred_at` | `timestamptz` | `not null default now()` | |
| `note` | `varchar(500)` | nullable | "Take-home sent", "ghosted". |

Plus: `create index ix_application_event_application_id on application_event (application_id);`
→ **Postgres does not index foreign keys automatically.** This index is the reason the timeline
query and the cascade delete stay cheap, and it is a great thing to know.

This table is what makes the model relational rather than a spreadsheet: it turns "status" from
a value into a **history**, which gives me "12 days in INTERVIEW", an audit trail, and a real
`@OneToMany` with a fetch-strategy decision (`LAZY`, loaded by an explicit query — the N+1
conversation).

### Deferred: `company` (feature 005, only if hours remain)
I want to keep company research — mission, vision, notable projects, Glassdoor score.
**Those are attributes of the company, not of my application to it.** Putting them on
`application` would repeat them across every application to the same employer and let them drift
apart the moment I update one row and not the others — the classic update anomaly. So the choice
is not "table or columns", it is **"model it properly or don't store it yet"**, and at 18 hours
the honest answer is not yet: a `company` table costs a lookup endpoint, a create-or-find rule,
a picker in the form and a screen to edit the research.

Deferring is not the same as forgetting. The design, ready to build:

```sql
-- V3__add_company.sql
create table company (
  id             bigint generated by default as identity primary key,
  name           varchar(120) not null,
  mission        text,
  vision         text,
  notable_work   text,
  glassdoor_score numeric(2,1) check (glassdoor_score between 0 and 5),
  website_url    varchar(512),
  created_at     timestamptz not null default now(),
  updated_at     timestamptz not null default now()
);
create unique index ux_company_name on company (lower(name));

-- backfill from what is already there, then link
insert into company (name) select distinct company_name from application;
alter table application add column company_id bigint references company(id);
update application a set company_id = c.id
  from company c where lower(c.name) = lower(a.company_name);
alter table application alter column company_id set not null;
alter table application drop column company_name;   -- only after the code stops reading it
```

That backfill is the single best learning exercise left in the project: a **data** migration on
live data, `@ManyToOne` with a lazy fetch, and a two-step deploy (add the column, ship the code,
then drop the old one) — the expand/contract pattern, which is a real interview topic. Doing it
in week 3 on data that already exists teaches more than having had the table since day one.

## 3. API — 8 endpoints

Base `/api`. Errors are RFC 9457 `ProblemDetail`.

| # | Method | Path | Returns | Notes |
|---|---|---|---|---|
| 1 | `GET` | `/api/applications` | `200` list of `ApplicationSummary` | No query params. The whole board is a few hundred rows; **filtering and search happen in Angular with `computed()`** — that is the point of the frontend learning goal. |
| 2 | `GET` | `/api/applications/{id}` | `200` / `404` | |
| 3 | `POST` | `/api/applications` | `201` + `Location` / `400` / `409` | 409 = duplicate company + title. |
| 4 | `PUT` | `/api/applications/{id}` | `200` / `400` / `404` / `409` | Full replace. |
| 5 | `PATCH` | `/api/applications/{id}/status` | `200` / `404` / `409` | The board move. Validates the transition, writes an `application_event` in the **same transaction**. 409 on an illegal transition (e.g. `REJECTED → OFFER`). |
| 6 | `DELETE` | `/api/applications/{id}` | `204` / `404` | Cascades the events. |
| 7 | `GET` | `/api/applications/{id}/events` | `200` list, newest first | |
| 8 | `GET` | `/api/me` | `200 {username}` / `401` | Tiny, but it is how the UI knows the credentials work across origins, and it forces me to read the `SecurityContext`. |

`/actuator/health` is exposed (not counted) — Render's health check and the keep-warm ping use it.

**No `/api/stats` endpoint.** Per-column counts, totals and the funnel are `computed()` over the
list the browser already has. Deliberate: a stats endpoint would be an easier server and a worse
lesson.

Transition rules (the only real domain logic, and therefore the only thing worth a Mockito test):
```
WISHLIST  → APPLIED | REJECTED
APPLIED   → INTERVIEW | REJECTED
INTERVIEW → OFFER | REJECTED | INTERVIEW   (self-move = next round)
OFFER     → REJECTED
REJECTED  → (terminal)
```

## 4. Screens — 2, plus one dialog

1. **Board** — mobile: a segmented control with the five statuses and their counts, one column
   of cards visible at a time. Desktop (≥1024 px): the five columns side by side. Header with a
   search box and a source filter. Column counts, filtered lists and the empty state are all
   `computed()` from one `signal` holding the applications. Status changes through a menu on the
   card — **no drag-and-drop**: correct on touch, reachable by keyboard, and free.
2. **Detail** — a route, not a modal (a full-screen route is the right pattern on a phone):
   read-only header, the edit form (Angular 22 **Signal Forms**, with Reactive Forms as the
   fallback if they fight me for more than an hour), and the event timeline. `linkedSignal`
   holds the editable draft so it resets when the selected application changes.
3. **Auth dialog** (not a screen) — username + password held in an in-memory `signal`, sent as
   an explicit `Authorization: Basic …` header on writes. No storage, no cookie, no token.
   Closing the tab logs you out, which is exactly right for a single-user demo.

## 5a. Privacy — why the public board is fake

A job-application tracker is a **private** dataset. Published, it would show which companies
rejected me, that I am at final stage with one employer while another reads the page, my salary
range, and free-text notes that may name a recruiter. That is a privacy leak and a negotiating
disadvantage, and it is not fixed by "nobody will look".

So the app runs in two environments, with the same code and different data:

| | public | private |
|---|---|---|
| where | Cloudflare Pages + Render + Neon | laptop: `docker compose up` + local Postgres |
| data | invented companies, invented salary bands, loaded by the `demo`-profile Flyway seed | my real applications |
| reads | public — recruiters see a full board | me only |
| writes | authenticated; credentials not published | me only |

Rules that keep them apart:
- **The local app is never pointed at the Neon connection string.** One `.env` mistake is all it
  would take. Real values live in a git-ignored `.env`; `.env.example` documents names only; the
  production string lives in Render's environment variables.
- The demo seed migration never runs against a database holding real rows — it is bound to the
  `demo` profile, not to `default`.
- Seed data uses **invented** employers. A public board reading "Rejected by <real company>" is
  read as real whether or not it is, and it looks unprofessional at best.
- A "Demo data" chip sits in the header of the deployed app, and the README says the same thing.

This is not a workaround for a flaw in the plan; it is how production and demo environments
normally differ, and saying so is a good answer.

## 5. Non-functional, and the honest ones
- **Mobile-first is a requirement, not a polish step.** Designed at 360 px. Checked on a real
  phone at feature **002**, when it first goes live — not at the end.
- **First load may take ~60 s** (free API instance wakes from sleep). Therefore: skeleton
  loading state everywhere, and a line in the README saying so. An unexplained 60 s blank page
  is a worse portfolio signal than no deploy.
- Public read, authenticated write. Demo credentials are **not** published — a recruiter sees a
  full board, nobody can vandalise it.
- Keyboard-reachable status change. Visible focus rings. Tap targets ≥ 44 px.
- CI must be red on a failing test and must run the Testcontainers integration tests.

## 8. Risks
| risk | mitigation |
|---|---|
| WSL + Docker + JDK + Node yak-shave eats hours 1–3 | Done at hour 0, off the clock: Java 25 ✓, Node bumped to ≥24.15 (the Angular 22 floor), Docker Engine + Compose v2 installed natively in WSL with systemd enabled, `docker run --rm postgres:17 postgres --version` green. No global Maven — `./mvnw` only. |
| Tests can't find Docker | Run everything **inside WSL**. From Windows, Testcontainers cannot reach `/var/run/docker.sock`. |
| Java 25 is newer than most tooling examples | Spring Boot 4.1 supports 17–26, so this is supported, not bleeding-edge. Expect one wrinkle: Mockito's agent warning, fixed once with `-XX:+EnableDynamicAgentLoading`. The code stays source-compatible with 21. |
| CORS preflight returns 401 | The CORS config must be **inside** the Spring Security chain (`http.cors(...)`), not a standalone filter; `OPTIONS` must never reach the auth filter. Budgeted, and the single most likely place to lose an evening. |
| Copying Spring Boot 3.x patterns | See AGENTS.md. Check the version in every docs URL. |
| Testcontainers slow / flaky in WSL | One reusable container; run `./mvnw verify` before pushing, not on every save. |
| Claude Code writes code faster than I understand it | Definition of done #6. If I can't say it out loud, the feature is not done, and the fix is to read, not to ship. |
| `docs/study/**` is git-ignored → no backup | Accepted knowingly; back it up manually near the end of the project. It stays out of the public repo — recruiters must never find the cheat sheet. |
| Free-tier terms change mid-project | Neon free (0.5 GB, 100 CU-h, no card) and Render free (750 instance-h, spin-down after 15 min idle) checked Aug 2026. **Never create a Render Postgres — it expires after 30 days.** The DB is Neon. |
| 6 h/week leaves no room for a bad week | The cut list in §7 exists so that a bad week costs scope, not the deadline. |
